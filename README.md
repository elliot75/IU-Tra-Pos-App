## 啟動

需要 Node.js 22 以上，先安裝套件：

```bash
npm install
```

將 `.env.example` 複製成 `.env`，依自己的開發環境填寫。啟動：

```bash
npm run dev
```

在 `http://127.0.0.1:3000` 開啟點餐畫面，`/admin` 為商品管理，`/operations` 為營運工作台。營運 API 另以登入、設備秘密、門市綁定及逐項權限檢查，不會自動授權既有員工；工作台靜態頁可開啟不代表營運服務已啟用。完整正式權限部署與安全驗收尚未完成，不可直接公開此開發服務。

登入、登出、目前員工及商品管理 API 預設使用 `AUTH_TRANSPORT_MODE=https-proxy`，連 loopback HTTP 都不視為 TLS；目前 LAN HTTP 因此不能登入。直接 TLS socket 可通過；反向代理則必須同時符合連線來源在 `TRUSTED_PROXY_IPS` 的明確 IP 清單內，以及單一 `X-Forwarded-Proto: https`。清單以逗號分隔，不接受主機名稱、CIDR 或萬用字元，空清單不信任任何代理；無效模式或 IP 設定會阻止啟動。

部署 HTTPS 反向代理時，必須覆寫（不可附加或沿用客戶端值）`X-Forwarded-Proto`，依代理實際接收的協定設定；並覆寫 `X-Real-IP` 為代理驗證的客戶端單一 IP。代理應拒絕 HTTP 登入請求。將應用 `HOST` 綁定 loopback（代理同機時），或以防火牆／容器網路只允許指定代理連入，阻擋客戶端直接連線。只有可信代理的單一有效 `X-Real-IP` 用於來源限流，其他情況以 socket 來源 IP 計數，忽略 `X-Forwarded-For`。可信代理未正確覆寫標頭會破壞安全邊界。

僅在本機開發時，明確設定 `AUTH_TRANSPORT_MODE=local-development`、`HOST=127.0.0.1`，並維持 `TRUSTED_PROXY_IPS=` 空白，才允許 loopback HTTP 登入；此模式不開放 LAN HTTP。登入來源每個 60 秒固定視窗最多嘗試 10 次（含成功及格式錯誤），第 11 次回傳 429。每個程序最多保留 10,000 個來源，每次請求清理過期記錄，容量滿時拒絕新來源，避免淘汰活躍記錄而繞過限制；重啟會重設，多程序部署須另設共用限流。

自己的可信區網測試可在伺服器 `.env` 設定以下內容後重新啟動服務，保留原有的 `DATABASE_URL`：

```dotenv
HOST=0.0.0.0
PORT=3000
AUTH_TRANSPORT_MODE=lan-development
TRUSTED_PROXY_IPS=
```

之後可直接開啟 `http://192.168.10.20:3000/admin`（依伺服器實際 IP 調整）。此模式允許 loopback、IPv4 私有網段 10/8、172.16/12、192.168/16、指定的 Tailscale IPv4 網段 100.111.0.0/16，以及 IPv6 ULA 來源的 HTTP 管理操作；不採信轉發標頭來放行來源。帳號、權限與限流仍需通過。密碼與 token 在 HTTP 上未經 TLS 加密，僅供可信區網開發測試，不用於公開部署；改回 `AUTH_TRANSPORT_MODE=https-proxy` 並重啟即可恢復 HTTPS 要求。前端送出密碼前會先查詢伺服器是否允許 HTTP 登入。

執行測試（HTTP 整合測試自行明確啟用本機模式；安全傳輸測試自行指定安全模式）：

```bash
npm test
```

`npm test` 不載入 `.env`，測試自行建立模擬服務或隔離的 PGlite 資料庫，不使用目前門市的真實 PostgreSQL。營運測試的 PGlite 是真實 PostgreSQL 引擎，可驗證 SQL、DDL、約束、交易回滾及故障注入；測試轉接器只有單連線且序列化整筆交易，即使使用 `Promise.all` 也不能證明原生 PostgreSQL 多連線併發與鎖定正確。既有商品資料庫模擬測試亦不等於真實 PostgreSQL 整合驗收。

## PostgreSQL 與初始化

在 `.env` 自行設定 `DATABASE_URL`，不要提交 `.env` 或將密碼寫入文件。跨網路資料庫連線應使用經驗證的 TLS，依資料庫供應商指示設定連線字串與 CA。`GET /api/v1/health` 僅執行 `SELECT 1`，顯示連線狀態，不會檢查資料表是否已初始化。舊版 `ADMIN_API_TOKEN` 不再提供後台存取權。

應用程式啟動時不會自動建立或修改資料庫。[migrations/001_catalog.sql](migrations/001_catalog.sql) 是全新安裝 SQL，會建立 `iutra_pos` schema、草稿及發布快照表；同名 schema 已存在會報錯，不應重跑。執行前須確認目標、盤點既有 schema、備份並取得變更權限，先在獨立測試副本驗證；既有結構需要映射時不要直接套用。營運 SQL 已有 PGlite 引擎驗證，原生 PostgreSQL 多連線、權限部署與復原仍待實測。正式部署須分離應用、遷移、設定及備份角色，見[維運說明](docs/operations.md)。

[migrations/002_staff_auth.sql](migrations/002_staff_auth.sql) 是員工帳號與登入狀態的手動遷移，須先確認 `001` 已安裝、目標與備份正確後，由有權限的維運人員審閱執行。程式不會自動執行此遷移。完成後可由維運人員手動建立具有商品管理權的具名帳號，密碼由終端輸入且不顯示：

```bash
node --env-file-if-exists=.env scripts/create-staff.js manager '店長' --can-manage-catalog
```

帳號與顯示名稱請依實際需要替換。商品管理頁以具名帳號登入後，先儲存草稿再發布；草稿有版本衝突時需重新載入。登入過期時，以同帳號在本頁重新登入可保留尚未儲存的草稿及原版本；重新整理或關閉頁面仍會丟失未儲存草稿。點餐畫面載入目前已發布版本，若不可用可主動選擇範例菜單。

## 營運工作台（預設停用）

先確認測試副本及變更範圍，再由維運人員手動審閱執行 [004_operations.sql](migrations/004_operations.sql)；它依賴 `001`、`002`，不依賴實驗草稿 `003`，不會自動執行或自動建立帳號／授權。依 [config/pos.example.json](config/pos.example.json) 準備排除 Git 的 `private/pos-config.json`，替換 UUID、設備秘密與實際帳號；錢包／退款政策預設維持停用。

```bash
node scripts/configure-pos.js private/pos-config.json --check
node --env-file-if-exists=.env scripts/configure-pos.js private/pos-config.json --apply
```

`--check` 僅驗證格式，不連資料庫，也不確認帳號存在或部署權限。`--apply` 才連線並以交易更新指定門市、設備與授權；未列出的既有授權保留，撤權須明確列出該帳號並設 `permissions: []`。收銀帳號建立時不要加 `--can-manage-catalog`，設定角色用 `cashier`，不得給主管／管理資金權限。

啟用測試需設定 `ENABLE_POS_OPERATIONS=true` 與至少 32 字元的穩定隨機 `POS_REQUEST_HMAC_KEY`，再重啟；不要每次啟動重產金鑰。從點餐頁「前往結帳」送入工作台後，仍須登入、提供受授權設備、開班並在服務端保存訂單，才可建立付款請求。工作台有現金找零、銀行 QR 與人工核帳、政策控制的本金儲值／扣款／退款、異常款及補入帳、製作狀態、列印工作、班次報表與 CSV；顯示 QR 不會自動確認到帳，列印工作不會直接驅動硬體。

加密備份另需獨立的 `POS_BACKUP_KEY_BASE64`（32 bytes 金鑰的 Base64）。工具從專案根目錄收集資料庫與 `public/catalog-images/`：

```bash
node --env-file-if-exists=.env scripts/backup-pos.js backup private/backups/pos-20261106.iutrabak
node --env-file-if-exists=.env scripts/backup-pos.js stage-restore private/backups/pos-20261106.iutrabak private/backups/staging-20261106
```

備份父目錄需事先建立，輸出檔與 staging 目錄須為全新名稱。`backup` 需要 `pg_dump`；`stage-restore` 只驗證及解密至新目錄，不連線、不執行 `pg_restore`、不覆寫 DB 或目前圖片，也不是還原驗收。請另保管兩種金鑰、設備秘密與部署設定；備份包不含 `.env`、HMAC key 或設備秘密。完整先決條件、API 欄位與恢復流程見[營運文件](docs/operations.md)。

## 開發用訂單草稿 API

訂單草稿 API 預設停用，僅供獨立開發／測試環境驗證，尚未完成門市、設備及班次權限，也不支援付款、修改、取消、退款或正式開單。使用前須先確認獨立測試資料庫、備份與權限，審閱並手動執行 [003_order_drafts.sql](migrations/003_order_drafts.sql)；程式不會自動執行遷移。只有設定 `ENABLE_EXPERIMENTAL_ORDER_DRAFTS=true` 並重啟後才能使用 API，正式環境請維持停用。

已登入員工可透過 `POST /api/v1/order-drafts` 傳入 `operationId`（UUID）、`menuRelease` 和 `items`，服務端重新計價後保存快照（包含配料的販售單位）；超過 32 層的巢狀輸入在開啟交易前以 400 拒絕，示範菜單與非當前發布版本不可建立新草稿。相同員工重試相同 `operationId` 與內容會取回同一草稿，不同內容則回衝突。`GET /api/v1/order-drafts/{id}` 僅可讀取目前員工建立的草稿。兩個端點沿用管理 API 的傳輸保護與登入驗證；草稿不代表已付款或已接受正式訂單。資料庫遷移、實際 PostgreSQL 並行及故障恢復尚未實機驗證。

## 目前功能與限制

- 商品可設定甜度、冰量等選項群組、選擇數量及預設選項；預設不足最低選擇數時，點餐需補選。點餐時由伺服器檢查，選項目前不加價；互斥條件尚未支援。菜單目前是全系統單一草稿及發布版本，尚未支援門市、啟用排程或停售；商品可設定公開的 HTTPS 圖片網址或已匯入的本機商品圖片路徑，儲存並發布後顯示於點餐菜單，清空網址可移除圖片。圖片失效時會顯示替代圖案，不影響點餐；目前不支援上傳。匯入的圖片檔位於 `public/catalog-images/`，不包含在 Git 中；部署及備份時須與資料庫一併複製與保留，發布版本只保存圖片路徑。分類及商品名稱目前須輸入中越文，正式語言政策仍待確認。
- 店員點餐畫面可依中文或越文商品名稱搜尋，與分類篩選同時使用；越文搜尋不區分大小寫與聲調。切換菜單時搜尋與分類會重設。
- 伺服器使用整數 VND 計價，API 金額使用十進位字串；菜單版本不符時拒絕試算，不採信瀏覽器傳入的價格。
- 規格範例：烏龍茶 500 ml 22,000₫、700 ml 24,000₫；示範配料 5,000₫。配料名稱及上限僅供測試，並非正式菜單。
- 顧客螢幕支援「僅顯示」與「顧客點餐」開發模擬，由主畫面切換，重新整理回唯讀。兩種模式顯示伺服器試算的明細；觸控加入先驗證與計價，過期操作拒絕。營運工作台可將核對／等待付款／完成／異常狀態與銀行 QR 投影至原點餐頁及客顯，結帳時鎖定顧客加單。QR 須由工作台取得，掃碼仍須人工核帳。此串接限同瀏覽器、同來源分頁，須由主畫面配對，重整後需重新建立有效連線；分頁配對識別不是設備身分認證。模式持久化、實體設備配對、獨立雙屏與實掃仍待驗收。
- 店員可修改或複製點餐明細，複製後各筆的規格、選項、配料及備註可分別調整；每次變更均由伺服器重新試算。修改明細須等試算成功才取代原內容；失敗或逾時會保留原訂單與編輯輸入，可直接重試。儲存修改期間暫停編輯操作，請求最長等待 10 秒。編輯期間若訂單已變更，會要求重新選擇，避免覆蓋顧客或店員的新操作。這些操作目前只在主畫面提供，顧客端編修範圍仍待確認。
- 點餐明細可分別輸入顧客可見備註及內部備註；前後端共用單行備註驗證，客顯只接收顧客可見備註。新增、修改及複製前會檢查整張訂單的 UTF-8 請求大小（上限 64 KiB），超限時保留原訂單；試算失敗仍可逐筆移除。開發用訂單草稿的伺服器計價快照也會保存兩種備註。
- 點餐頁的伺服器請求包含讀取回應，均有 10 秒期限；顧客加入失敗或逾時會釋放操作鎖，晚到結果不再加單。顧客操作結果最多快取 1,000 筆，回收後仍以原畫面版本拒絕過期重播。成功加入直接使用服務端報價，不重複試算。菜單驗證由前後端共用，客顯首次連線或菜單版本改變才傳完整菜單；相同畫面版本使用輕量心跳。
- 點餐頁試算仍不是收款；送入營運工作台後才會持久化至營運訂單及帳務表。工作台在送出寫入前於分頁儲存保存原操作識別與非秘密內容，逾時／重整後以原員工及設備查詢或同鍵重試；PIN、密碼、token 不寫入該紀錄。這是線上結果恢復機制，並非離線收款資料庫，關閉分頁或清除儲存可能遺失待確認線索。
- 營運能力已實作但預設停用；本金錢包與退款還須明確設定核准政策。銀行自動通知、實體印表機／錢櫃 sender、主管手動開櫃、離線持久化與同步、跨店錢包／清算、混合付款及電子發票未完成。菜單仍無門市覆寫、排程、售罄管理；不能將資料結構預留當成已完成多店營運。
- 2026-11-06 已唯讀盤點 PostgreSQL 17.10／`iutra_pos` 五表，並依授權完成一次性商品與圖片匯入、菜單發布：來源 64 商品／103 規格／8 分類，保留原資料後為 65 商品／9 分類；63 圖片參照對應 58 個去重檔。這不是會員、錢包或歷史帳務匯入授權；私密來源與回執位於排除 Git 的 `private/posapp-audit/`。目前沒有常設同步或圖片上傳模組。
- 自動測試涵蓋 PGlite 營運 SQL、約束及故障注入，也有模擬連線及前端邏輯測試；不等於原生 PostgreSQL 併發、完整瀏覽器／實機、銀行、離線或資料庫還原驗收。詳細完成、停用與待驗收範圍見[實作狀態](docs/implementation-status-v1.1.md)。
